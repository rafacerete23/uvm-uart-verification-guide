UVM UART Verification Guide

Aprende a verificar un UART 8N1 con un testbench UVM de dos agentes, paso a paso y con simulador interactivo.

SystemVerilog UVM Verilator 5 UART 8N1 CLKS_PER_BIT=16 Autor: Rafael Acerete repo: uvm-uart-verification-guide

1. Qué vamos a verificar

El DUT es rtl/uart_core.sv: un núcleo UART 8N1 con el parámetro CLKS_PER_BIT=16 (frecuencia de reloj dividida entre el baud rate).

Transmisor (TX)

  • Acepta un byte cuando tx_valid && tx_ready.
  • tx_ready está alto solo cuando el transmisor está libre.
  • Trama: bit de start = 0, 8 bits de datos LSB primero, bit de stop = 1.
  • Cada bit dura CLKS_PER_BIT ciclos de reloj.

Receptor (RX)

  • rxd pasa por un sincronizador de 2 flip-flops.
  • Detección de start por flanco de bajada, validada a mitad de bit: los glitches más cortos que medio bit se rechazan.
  • Datos muestreados a mitad de bit, LSB primero; el stop también se muestrea a mitad de bit.
  • stop=1 → rx_valid pulsa un ciclo con rx_data.
  • stop=0 → rx_frame_err pulsa un ciclo (sin rx_valid) y el receptor espera a que la línea suba antes de buscar un nuevo start.

5. Tests y cobertura

uart_tx_test

Envía bytes por el camino TX y comprueba que las tramas decodificadas desde txd coinciden con los bytes aceptados.

uart_rx_test

Inyecta tramas válidas en rxd y verifica rx_valid y rx_data.

uart_error_test

Usa bad_stop: el stop es 0 y debe pulsar rx_frame_err sin rx_valid.

uart_glitch_test

Inyecta un glitch más corto que medio bit: el receptor debe rechazarlo.

uart_full_duplex_test

TX y RX activos a la vez; valida ambos caminos y la cobertura.

uart_coverage

Recolecta cobertura funcional de los escenarios anteriores.

Clase 1 — Tolerancia de baudrate

Cuánto puede desviarse el reloj del emisor antes de que el receptor 8N1 lea mal los datos.

Por qué hay tolerancia

Emisor y receptor usan relojes distintos. No hay línea de reloj compartida.

El receptor sincroniza con el flanco del start y muestrea cada bit CLKS_PER_BIT = 16 ciclos después.

El error se acumula a lo largo de 9,5 bits (del flanco del start al centro del stop).

Regla clásica: error < 0,5 bit → ±0,5 / 9,5 ≈ ±5,26 %.

En la práctica se deja margen. Un divisor entero de 16 ciclos/bit solo permite pasos de 1/16 = 6,25 % en el periodo del bit.

Qué pasa en este RTL

El RTL muestrea el bit de datos k a los 25 + 16·k ciclos desde el flanco del start, y el stop a los 153.

El centro ideal del dato k sería 24 + 16·k: el muestreo cae ~1 ciclo tarde (2 FF de sincronización + ciclo de detección).

Modelo: dato k correcto si j = k+1. El peor es D7 (t = 137): correcto si 128(1+s) ≤ 137 < 144(1+s) → s ∈ [−4,9 %, +7,0 %].

Stop (t = 153): correcto si 144(1+s) ≤ 153 → s ≤ +6,25 %.

Ventana combinada del modelo: ≈ −4,9 % … +6,25 %. La asimetría viene del ciclo de retraso.

Ventana medida en Verilator: −4,5 % … +6,0 %.

Cómo se verifica

El self-check añade drive_frame_skew: genera tramas con el bit desviado skew_pm milésimas, con fronteras enteras.

Frontera del bit i: ((i+1)·CLKS_PER_BIT·(1000+skew_pm))/1000 ciclos.

5 desvíos (−4,0 %, −2,5 %, +2,5 %, +4,0 %, +5,5 %) × 14 tramas (00, FF, 80, 01 y 10 aleatorias) = 70 tramas, todas comparadas por el scoreboard.

task automatic drive_frame_skew(input logic [7:0] data, input int skew_pm, input int idle_clks);
  int elapsed = 0;
  int boundary;
  int num;
  // bit 0 = start, 1..8 = datos LSB primero, 9 = stop
  for (int i = 0; i < 10; i++) begin
    if (i == 0)      rxd = 1'b0;          // start
    else if (i == 9) rxd = 1'b1;          // stop
    else             rxd = data[i-1];     // datos LSB primero
    // frontera del bit i (fin del bit i) en ciclos desde el inicio de la trama
    num = (i+1) * CLKS_PER_BIT * (1000 + skew_pm);
    boundary = num / 1000;
    repeat (boundary - elapsed) @(posedge clk);
    elapsed = boundary;
  end
  // idle tras el stop
  rxd = 1'b1;
  repeat (idle_clks) @(posedge clk);
  // ... (se añade el evento esperado a exp_q)
endtask

Resultado medido

Barrido en Verilator 5.052: recibe todo bien de −4,5 % a +6,0 % (22 puntos OK).

Falla en −5,0 % y por debajo: datos corruptos sin error de trama (8 tramas recibidas, 0 errores).

Falla en +6,5 % y por encima: 4 de las 8 tramas dan error de trama (las de D7 = 0).

Con +6,5 % el stop se muestrea dentro de D7; si D7 = 0 se lee stop = 0 → rx_frame_err.

Con −5 % D7 se muestrea ya dentro del stop y se lee un 1 en vez de D7 → dato corrupto silencioso.

Self-check con drive_frame_skew: RESULT: PASS con 366 tramas RX (296 + 70).

Mutación real: cambiar el umbral de validación del start de (CLKS_PER_BIT/2)-1 a (CLKS_PER_BIT/2)+3 (muestreo 4 ciclos más tarde). El self-check antiguo seguía dando PASS; el nuevo da FAIL (22 errores).

Barrido reproducible con bash sim/run_baud_sweep.sh.

Nota: es el testbench plano, no UVM (UVM sigue sin ejecutarse en ningún simulador). El modelo de la ventana está deducido del RTL y coincide con la medida en los puntos de 0,5 % probados.

7. Ejercicios guiados

Ejercicio 1 — Longitud de la trama

Con CLKS_PER_BIT=16, ¿cuántos ciclos de reloj dura una trama completa (start + 8 datos + stop)?

Pista

Cuenta los bits de la trama y multiplica por CLKS_PER_BIT.

Solución

10 bits × 16 = 160 ciclos de reloj por trama.

Ejercicio 2 — ¿Por qué muestrear a mitad de bit?

Explica por qué el receptor muestrea en el centro de cada bit y no en el borde.

Pista

Piensa en la tolerancia a diferencias de reloj y en los glitches.

Solución

El centro del bit es el punto más alejado de las transiciones, así se toleran pequeñas diferencias de frecuencia entre emisor y receptor y se evita muestrear un glitch o un borde inestable. Además, validar el start a mitad de bit rechaza glitches más cortos que medio bit.

Ejercicio 3 — Secuencia back-to-back de 0x55

Escribe una secuencia que envíe 0x55 varias veces seguidas y explica qué compara el scoreboard.

Pista

0x55 = 8'b01010101, alterna bits. El scoreboard TX compara host_ap vs line_ap.

Solución

La secuencia hace repeat(N) `uvm_do_with(req, {data == 8'h55;}). El scoreboard TX compara cada byte aceptado por el host (host_ap) con la trama decodificada desde txd (line_ap): mismo dato, LSB primero, start=0 y stop=1. En RX compara las tramas inyectadas (in_ap) con rx_valid/rx_data o rx_frame_err (out_ap).

Ejercicio 4 — Tolerancia teórica con muestreo ideal

Un UART 8N1 muestrea cada bit exactamente en su centro. ¿Qué desviación máxima entre el baudrate del emisor y el del receptor puede tolerar sin leer mal ningún bit? Expresa el resultado en porcentaje y explica de dónde sale la cifra clásica de ±5 %.

Pista

El error de temporización se acumula desde el flanco de bajada del bit de start hasta el centro del bit de stop. ¿Cuántos periodos de bit hay entre esos dos instantes? Compara ese error acumulado con la mitad de un bit.

Solución

El centro del stop está a 9,5 bits del flanco de bajada del start (1 bit de start + 8 de datos + 0,5 del stop). Para no leer mal ningún bit, el error acumulado debe ser menor que medio bit: 0,5 / 9,5 ≈ 5,26 %. De ahí la cifra clásica de ±5 %: en la práctica se deja margen para jitter, asimetrías de flanco y otros errores del receptor.

Ejercicio 5 — Predice el fallo con +6,5 % y con −5,0 %

Este RTL muestrea el bit de datos k (k=0..7) a los 25+16k ciclos del flanco de bajada de rxd, y el stop a los 153 ciclos. Un emisor con periodo de bit N = 16·(1+s) coloca el bit i (0=start, 1..8=D0..D7, 9=stop) en [N·i, N·(i+1)). Usando esos instantes, predice qué bit se lee mal y qué síntoma observa el scoreboard (¿error de trama o datos corruptos?) con +6,5 % y con −5,0 %. Indica además qué bytes de la lista 00 FF 55 AA 80 01 7F FE se ven afectados en cada caso.

Pista

Calcula N en cada caso. Para el stop compara su inicio 9N con t=153 (instante de muestreo del stop). Para D7 compara 9N con t=137 (instante de muestreo de D7). ¿Dónde cae el muestreo, dentro del bit correcto o dentro del vecino?

Solución

+6,5 %: N = 16·1,065 = 17,04. El stop empieza en 9N = 153,36 > 153, así que a t=153 el receptor todavía está dentro de D7: si D7=0 lee stop=0 y se dispara rx_frame_err. Afecta a los bytes con D7=0 de la lista (00, 55, 7F, 01), es decir 4 de los 8, que es justo lo medido.
−5,0 %: N = 16·0,95 = 15,2. D7 se muestrea a t=137, pero el stop empieza en 9N = 136,8 < 137, o sea que a t=137 ya estamos dentro del stop y se lee un 1: el byte llega sin error de trama pero con el bit 7 forzado a 1 (corrupción silenciosa); afecta a los mismos bytes con D7=0. Coincide con lo medido: 8 tramas, 0 errores de trama, datos mal.
Es un modelo deducido del RTL que coincide con la medida en estos dos puntos.

Ejercicio 6 — ¿Por qué calcular las fronteras con enteros acumulados?

El generador de tramas desviadas calcula la frontera del bit i como ((i+1)*CLKS_PER_BIT*(1000+skew_pm))/1000 en lugar de redondear el periodo de un bit y luego sumarlo repetidamente. Explica por qué esto importa y escribe la fórmula en SystemVerilog.

Pista

Con skew_pm=+55, el periodo real de bit es 16·1,055 = 16,88 ciclos. Si redondeases a 17 ciclos por bit, ¿cuál sería la desviación efectiva? ¿Cuántas veces se repite ese error a lo largo de una trama de 10 bits?

Solución

Con skew_pm=+55, 16·1,055 = 16,88. Si se redondease a 17 ciclos por bit, la desviación efectiva sería 17/16 − 1 = +6,25 %, no +5,5 %, y ese error se repetiría en cada uno de los 10 bits de la trama, acercando la prueba al límite de la ventana (medido: +6,0 % aún OK, +6,5 % ya falla) en lugar de ejercitar el valor que se pretendía. Calculando cada frontera como un entero acumulado, el error de cada frontera queda por debajo de 1 ciclo y no se acumula.

// tb/selfcheck_tb.sv (ejecutado en Verilator)
    int num, boundary, elapsed;
    for (int i = 0; i < 10; i++) begin
      num      = (i+1) * CLKS_PER_BIT * (1000 + skew_pm);
      boundary = num / 1000;
      repeat (boundary - elapsed) @(posedge clk);
      elapsed  = boundary;
    end

8. Conceptos clave

Agente UVM

Agrupa driver, monitor y sequencer. Aquí hay dos: uart_tx_agent y uart_rx_agent.

Scoreboard

Compara lo esperado con lo observado. TX: host vs línea. RX: inyectado vs salidas del DUT.

Monitor

Observa la interfaz sin manejarla y publica transacciones por analysis ports.

Coverage

Mide qué escenarios se han ejercitado: datos, errores de stop, glitches, full-duplex.
